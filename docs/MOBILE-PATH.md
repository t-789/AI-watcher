# 移动端迁移路线（为什么这个 demo 不是死路）

> 结论先说：**换到手机要重写的只有"采集适配器"一层，约占总代码量的 1/5；分析核心、记录契约、AI 层、数据格式零改动。** 这不是提前设计出来的，是 demo 里已经用两个适配器（真实 B 站 / 合成回放）验证过的分层。

## 1. 现在这一层为什么能换

```
适配器（平台相关）        记录契约（迁移资产）        核心与呈现（复用）
extractHomeFeed(doc)  →  ContentItem/Exposure/Action  →  buildSnapshot + /api/profile JSON + 抽屉
extractVideoPage(doc)     + origin(real|synthetic)      ↑ 手机端同一套
```

适配器的接口只有一件事：**把"用户此刻看得见的东西"变成记录**。它不知道主题怎么算、画像怎么统计、提示怎么写。所以：

- 合成回放适配器（`src/adapters/replay/**`）证明：换掉第一层，第二到第五层原样工作 —— 这条链路已经在 `npm run replay` 与 e2e 里跑过。
- 手机端适配器只要产出同样的 `items/exposures/actions`，服务端与分析核心一行不用改。

## 2. 逐层替换点与成本

| 层 | 现在 | 手机端要换成 | 工作量 | 主要风险 |
| --- | --- | --- | --- | --- |
| ① 采集 | MV3 内容脚本读 DOM | **Android**：AccessibilityService 读无障碍树（拿到的是文本节点，不含视频内容）；**iOS**：分享扩展 / 屏幕使用时间 API + VisionKit OCR（需要用户授权） | 高（各平台 1—2 周） | 系统权限门槛、跨 App 抓取合规性、字段稳定性远不如 DOM |
| ② 记录契约 | JSONL/SQLite | 原样复用；手机上可先用 SQLite，再同步到桌面端 | 低 | 需要在同步时保留 `origin` 与 `data_mode` |
| ③ 分析核心 | Node 纯函数 | 原样复用；若要做端上离线分析，用 `react-native`/`Kotlin`/`Swift` 重写**同一批公式**（有 120 条测试当参照） | 中 | 重写要保住"半开区间窗口 / 计数不出负 / 确定性"三条 |
| ④ AI 层 | 本机 Node 调 DeepSeek | 直连 API 或走自家后端；缓存键与校验逻辑可复用 | 低 | 手机上不能存 key → 必须走后端代理或用户自填并加密存本地 |
| ⑤ 呈现 | 页面内悬浮球 + 抽屉 | **Android**：TYPE_APPLICATION_OVERLAY 悬浮窗；**iOS**：没有全局悬浮窗，只能做 App 内浮层 + 通知/小组件 | 中 | iOS 做不到"刷 B 站时旁边飘一个球"，这是硬限制，必须改产品形态 |
| 数据出口 | `/api/profile` JSON | 同一份 JSON 由 App 渲染 | 低 | — |

## 3. 平台硬限制（必须提前说清）

1. **iOS 没有跨 App 悬浮窗。** 想在 iOS 上贴着 B 站 App 浮一个球，做不到。可行形态：App 内浮层 + 屏幕使用时间报表式回顾 + 小组件。
2. **屏幕阅读权限**：Android 靠无障碍服务（用户手动开启，且系统会持续提示）；iOS 靠屏幕使用时间/Family Controls API（需要用户授权与家长式配置）。**用户不授权就没有自动采集**，只能走"分享链接到本 App"的降级路径。
3. **App 内内容 vs 网页**：B 站 App 的推荐流不在无障碍树里逐条暴露标题（列表是原生控件，可拿到文本但字段比 DOM 少），手机端可拿到的信号比 web 少，需要接受更粗的粒度（标题为主，简介/评论多半拿不到）。这正是"只凭可见元信息推断"这条边界的价值：**不需要读视频内容，所以手机上也不会变成高成本视频分析**。
4. **成本**：手机端采集频率高，AI 打标必须严格按内容哈希缓存 + 批量 + 限流；否则首页滚一分钟就是几十次请求。demo 里的缓存与批量参数（≤8 条/请求、并发 2、25s 超时）就是为此准备的。

## 4. 迁移时的实施顺序（建议）

1. 先在现有 Node 服务上做"手机适配器模拟"：写一个 mock 适配器，手机端字段子集（只有标题 + 作者 + 位置）喂进去，确认画像质量能接受 —— 这一步在 demo 里已经用回放适配器证明可行。
2. Android 无障碍服务先做"只读标题 + 去重"，跑一周真实数据，确认字段填充率与曝光去重口径。
3. iOS 用分享扩展做半自动采集（用户主动分享），验证"没有自动采集"时产品是否还有价值。
4. 端上分析能离线跑之后，再考虑把 ③ 的核心公式移植成 Kotlin/Swift，用现有 120 条测试当对照集。

## 5. 不承诺的事

不做跨 App 实时监测的完整实现、不做自动点赞/关注等账号操作、不声称读到平台内部兴趣标签、不把短期浏览习惯解释成固定人格。这三条在任何端上都成立，写进产品文案与答辩口径。
