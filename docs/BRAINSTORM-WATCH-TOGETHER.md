# Brainstorm：让 AI 低成本地"和用户一起看视频"

> 状态：头脑风暴（2026-11-03），没有实现，结论需要实测。
> 问题：现在只看标题、简介、热评，信息太少（尤其资讯/知识类，关键说法都在口播里）。难点是**成本**。

---

## 1. 先拆开"成本"：贵的不是 LLM，是"把视频变成文字"

| 环节 | 典型量（10 分钟中文口播视频） | 成本量级 |
| --- | --- | --- |
| 文字送 LLM | 口播约 2500—3500 字 ≈ 2—3k token | 很低：DeepSeek 这个量级是"分"以下（以现行价目为准） |
| 语音转文字（云 ASR） | 10 分钟音频 | 中：按分钟计费，天天看会累积 |
| 看画面（多模态模型） | 每秒 1 帧就是 600 张图 | **高**：比文字贵一到两个数量级 |
| 下载视频再处理 | 整个视频文件 | 高，而且违反项目"不拦截网络、不调内部接口"的承诺 |

所以低成本的核心思路只有一句：**尽量拿到现成的文字，不得已再自己转写，尽量不看画面，只处理用户真正看了的部分。**

---

## 2. 分层取材：从免费到昂贵，逐级升级

### 第 0 层：已有的元信息（现在就有，免费）
标题、简介、热评、UP 主、时长。够做主题打标和门控，不够做内容理解。

### 第 1 层：页面上本来就看得见的文字（几乎免费，**最推荐先做**）
- **字幕（CC / AI 字幕）**：B 站很多视频有 UP 主上传的 CC 字幕或平台自动生成的 AI 字幕。用户打开字幕时，播放器会把当前那句渲染进 DOM——content script 用现有的 MutationObserver 节拍顺手记下来，**随着用户看，逐句累积成字幕稿**，带时间戳（`video.currentTime`）。
  - 优点：零额外请求；与"只读屏幕上看得见的内容"口径一致（字幕本来就显示在屏幕上）；天然就是"陪看"——只拿到用户看过的部分。
  - 缺点：用户得开字幕；跳着看会缺段；不是每个视频都有。
  - 更进一步的做法是读播放器加载的完整字幕 JSON，但这属于"读平台内部数据/网络请求"，**跨过了现在的承诺边界**，需要组里决定。
- **弹幕**：屏幕上飘过的弹幕同样在 DOM 里，是时间对齐的"观众反应"。用途：发现争议点（"假的吧""前面说错了"这类弹幕集中出现的时间段，就是核验最该看的地方）、发现高光段落。
- **高能进度条 / 章节分段**：进度条上的弹幕密度曲线和 UP 主设置的分段标题都是现成的结构信息，可以拿来决定"哪几段值得细看"。
- **B 站自带的 AI 视频总结**：部分视频页有平台自己的 AI 总结入口，用户点开时内容在 DOM 里，可以直接借用（来源要标"平台生成"）。

### 第 2 层：本地语音转写（不花钱，花本机算力）
没有字幕时，用扩展的 `chrome.tabCapture`（MV3 下配合 offscreen document）抓**当前标签页的音频**，切成 30 秒片段发给本地的 ASR 进程转写。
- 模型候选：SenseVoice-Small（中文效果好、速度很快）、whisper.cpp、sherpa-onnx。在 Mac 上实时转写 10 分钟视频的算力开销很小。
- 架构上做成**可选的旁路进程**（比如单独的 Python 服务），不破坏主服务"零依赖"；没装就退回第 1 层。
- 注意：
  - `tabCapture` 需要用户手势触发（点一下扩展按钮）→ 正好对应"开启陪看"这个显式动作；
  - 抓取音频后标签页会静音，要把流再接回 `AudioContext` 播放出去；
  - 这一步确实在"处理视频内容"，要改 README 的承诺并让用户明确知情（本地处理、不上传音频）。

### 第 3 层：看画面，但只看极少几帧（按需付费）
只有当文字明显不够时才看图（例如图表、PPT 式科普、屏幕上的数据）。
- 取帧：`chrome.tabs.captureVisibleTab` 截可见区域（有频率限制），或把 `<video>` 画到 canvas（是否被跨域限制需要实测）。
- **先本地 OCR 再说**：很多中文视频是**硬字幕**（字压在画面上），本地 OCR（如 PaddleOCR、macOS 自带 Vision 框架）就能把它变成文字，等于免费的第 1 层。
- 真要调多模态模型：先用帧差/场景切换挑关键帧，每个视频 ≤ 5 张、压到低分辨率；只在"核验需要"或"用户就这一帧提问"时调用。

## 3. 控制用量的几个开关

1. **只处理用户真的看了的部分**：按播放进度增量处理，跳过的不处理。这既省钱，也符合"一起看"的语义——AI 不应该比用户"先看完"。
2. **门控复用**：沿用核验计划的门控（`content_type` + 主题），娱乐/vlog 只停在第 0—1 层，资讯/知识类才往上升级。
3. **按需而不是常驻**：默认只累积字幕稿，不调 LLM；用户在浮层里提问"刚才那句是真的吗？/这段讲了什么？"时，才把 **[t−60s, t] 的字幕窗口 + 元信息** 发给模型。成本 ∝ 提问次数，而不是观看时长。
4. **先压缩再发送**：长视频先在本地切段、只挑含数字/时间/人名/因果词的句子（和断言抽取同一套规则），再交给 LLM。
5. **缓存**：字幕稿与总结按 `BV号 + 分P + 片段序号` 缓存；同一个视频重看不再花钱。
6. **利用前缀缓存**：DeepSeek 等服务对重复的前缀（系统提示词）有更便宜的缓存命中价，保持 system prompt 固定不变、可变内容放后面。
7. **每日预算**：和核验共用一个预算闸门，超额就退回到更低层。

---

## 4. 它能解锁什么

- **核验从"标题党判断"变成"口播断言核验"**：断言抽取的输入从标题/简介换成字幕稿，`docs/PLAN-VERIFY.md` 阶段 1 基本不用改结构。
- **"营养价值"更有依据**：信息密度、是否有来源引用、情绪化程度可以按字幕稿估计，而不是只靠标题猜。
- **事件的多方位报道**（老师建议 1）：从字幕里抽出事件实体，去找别的角度的报道。
- **真正的"陪看"交互**：在某个时间点提问、看完一段自动给出"这段讲了 3 个要点，其中 1 个有争议"。

---

## 5. 推荐的落地顺序

1. **字幕 + 弹幕 DOM 采集**（第 1 层）：成本为零、与现有采集口径最接近，先做实测——统计真实浏览中有多少比例的视频能拿到字幕。
2. 用字幕稿喂核验的断言抽取（和核验计划阶段 1 合并）。
3. 字幕覆盖率不够，再上**本地 ASR 旁路**（第 2 层），作为用户显式开启的"陪看模式"。
4. 第 3 层（看画面）先只做本地 OCR 硬字幕，多模态模型放最后，且只按需。

---

## 6. 需要你拍板的问题

1. **边界**：README 的核心承诺是"不读视频内容"。读屏幕上显示的字幕/弹幕算不算违背？本地转写音频呢？建议的说法：*"默认只读屏幕上显示的文字；'陪看模式'由用户手动开启，音频只在本机转写、不上传"*，并同步改 README 与答辩口径。
2. **读完整字幕 JSON**（而不是逐句从 DOM 累积）可以接受吗？它更完整、更省事，但属于读平台内部数据。
3. **本地 ASR 引入 Python 旁路进程**可以接受吗？还是坚持全 Node、零依赖？
