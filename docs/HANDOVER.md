## 1. 一句话现状

一个能在**真实 B 站**上跑通的功能 demo：用户刷视频时，扩展采集"屏幕上看得见的内容"，本地服务做确定性统计 + DeepSeek 打标，右下角悬浮球点开就是**三画像对照**（平台给的 / 你点的 / 你写的目标）＋六条证据式提醒 ＋ 一组"可以点开看看"的推荐。

- 代码：62 个文件，10 次提交，工作区干净。
- 测试：`npm test` **212 / 212**；扩展静态检查 **17/17**。
- 真机验收：`tools/e2e/acceptance.mjs` **21/21**；刷新策略 `refresh-check.mjs` **11/12**；行为门槛补证 `behavior-session.mjs`（10 个视频 → `sample_n=10`、`D(U,P)=0.2427`）。
- 线上库（用户真实浏览）：243 条内容 / 307 次曝光 / 7 次行为；AI 缓存 217 条（打标按内容哈希复用）。

## 2. 现在能做什么

| 能力 | 用户看到的 | 说明 |
| --- | --- | --- |
| 采集 | 悬浮球上的"已采集 N 条 + 当前集中主题" | 只读 DOM：标题 / UP 主 / 时长 / 播放量 / 简介 / 热评；不读视频内容、不拦截网络 |
| 行为记录 | 抽屉「行为 vs 曝光」 | 只在用户**真的点开**视频时记 `open`，播放 ≥5s 才补 `watch`，搜索页记 `search`；同会话去重 |
| 目标 | 抽屉「我的目标」 | 一句话 + 意图模式 → AI 结构化成主题权重；关键词兜底；「放松」类诉求有确定性兜底（`applyRelaxIntent`，游戏/动漫/影视合计 0.4） |
| 画像 | 「主题分布」百分比条 + 折叠区里的熵 / 重复率 / 来源集中度 / `D(U,P)` / `D(G,P)` | 首屏只留结论、分布、建议、推荐、目标；其余收进「展开细节」 |
| 提醒 | 「结论」区 | 六条规则（输出集中 / 目标差距 / 行为差距 / 重复偏高 / 来源集中 / 范围收窄），门槛不满足时写明缺什么 |
| 建议 | 「建议」区 | 每条带 `topic`，证据必须同主题；库里没有同主题内容时给「去搜索：xxx」 |
| 推荐 | 「可以点开看看」 | 候选 = 刷到但没点开的内容（含搜索页结果），确定性贪心排序，AI 只写一句理由 |

## 4. 必须知道的口径（改代码前先读这段）

1. **曝光 P 只统计 `home` / `video_related`**。搜索页结果是你主动拉的，另计 `window.search_pull_count`，不进 P、不进熵/重复率/来源集中度。
2. **曝光去重按"访问"**：同一 `(session, page_context, canonical url)` 只算一次；换页或新会话才算新曝光——这样"重复曝光率"才真的在数重复。
3. **视频页的 `page` 只补全元信息**（简介/热评），不算曝光；用户点进去这件事记在行为侧（`open`）。
4. **`open` + `watch` 对同一内容合并成 1 个行为样本**，门槛 `minBehavior = 10`。所以短会话里 `U` 不可用是**设计**，不是 bug；界面必须写"有效正向行为 N 条，低于门槛 10"而不是硬给数字。
5. **阈值是演示校准值**（曝光 ≥20 / 已知主题 ≥60% / 熵 <0.45 / `D` >0.30 / 重复率 >0.35 / 单一来源 >0.40），比规划书的 50/80% 低，否则一次会话永远看不到提醒。界面与 `alerts[].thresholds_used` 原样披露，不冒充学术标准。
6. **合成数据必须标 `origin="synthetic"`**，界面常显 `data_mode`。演示库（`data-demo/`）与真实库（`data/`）分开，混用会得到 `mixed`。

```bash

# 装扩展：手动（持久，推荐）：chrome://extensions → 开发者模式 → 加载已解压 → 选 extension/

# 断网/无 key 演示（合成数据，data_mode=synthetic）
npm run demo

# 质量
npm test && node tools/check-extension.mjs
bash -lc 'source ~/.zshrc; node tools/e2e/acceptance.mjs'
```

**端口纪律（踩过的坑）**：3789 是用户真实使用的端口，任何自验/子任务一律用 3790 以上。曾有一次测试服务占用 3789，把用户真实浏览数据写进了临时库。

**数据在哪**：`data/aiwatcher.db`（SQLite）、`data/ai-cache.jsonl`（AI 打标缓存）。清空：抽屉「清空」或 `POST /api/reset`；搬走：`GET /api/export`（JSONL）。两者都在 `.gitignore` 里。

## 6. LLM 调用清单（全部集中在一处）

只有 `src/server/ai.js` 会发 LLM 请求（有静态断言锁住）。四个功能点：

| 功能 | 触发 | 每次量 | 缓存 |
| --- | --- | --- | --- |
| 内容打标 | 新内容入库 | ≤8 条/请求，并发 2 | 按 `sha1(title\|desc\|comments)`，重复曝光 0 请求 |
| 目标结构化 | 用户点「保存目标」 | 1 次 | 无（用户手动触发） |
| 叙述 + 建议 + 推荐理由 | 数据指纹变化时 | **1 次**（三者合并） | 按指纹；重复打开抽屉 0 请求 |
| — | 无 key / 报错 | 不发请求，走关键词与模板句，`why` 为 null | 降级结果**不写缓存** |

实测特征：数据不变连点两次抽屉 `requests` 不增；只有曝光变化 +1；全新内容 +2（1 打标 + 1 合并）。打标文本量很小（首页卡片只有标题），成本随**唯一内容数**增长，与曝光次数无关。

## 7. 已知限制与技术债

**影响用户**

1. **评论需登录态**：未登录时 B 站评论区只有"登录后查看"，`comments` 为空。抽取逻辑已用本地 DOM 复刻验证（8 条上限、穿透 `bili-comments` shadow root），未登录不绕过。
2. **未登录首页是大众热门流**，不是个性化推荐；画像要准必须登录。
3. **CDP 装载的扩展不跨浏览器重启**（Chrome 156 已忽略 `--load-extension`），长期用走 `chrome://extensions` 手动加载。
4. **手动刷新会丢焦点**（内容不丢）：refresh-check 11/12 的那 1 项。
5. **`minBehavior=10`** 意味着点 1—3 个视频算不出 `D(U,P)`，界面会说明缺多少证据。

**影响维护**

1. **`extension/extract.js` 是软链接**指向 `src/adapters/bilibili/extract.js`（DOM 规则只有一份）。macOS/Linux 正常，Windows clone 会断链。
2. **合成日志生成器已与目标解析解耦**：`generate.js` 自带冻结的目标向量。以后可以放心改目标算法，不会带偏 `fixtures/`（这个坑踩过一次，两个 determinism 测试红）。
3. **`--seed` 会清空服务同款库**（默认行为，会打印清了多少条）；`--append` 才追加。演示库务必独立 `--data-dir`。
4. **虚拟时钟**：合成数据时间戳晚于本机时钟时，服务用 `now = max(真实时钟, 最后一条记录时间)`，启动日志第 5 行会标 `(virtual, +12.9d)`。真实数据不受影响。
5. **建议 schema 在演进**：`topic / basis / evidence[{content_id,title,url,count}] / search{keyword,url}` 是后来加的（只增），扩展里不得硬编码搜索地址（地址一律由服务端给）。

## 8. 下一步：内容可信度核验（只叙述）

### 8.1 用户设定的目标

当用户点击一个内容时，帮助他判断这条内容**是否全面、客观**。具体设想：先判断当前观看的是哪类内容 → 如果是资讯/知识这类"事关对错"的内容，就上网搜索相关关键词求证 → 如果与事实不符/偏离/不完全正确，弹窗提醒并给出求证链接；如果是正确的，则只在用户点开弹窗时显示"内容无误"，并可推荐几个相关链接。

### 8.2 这件事在项目里的位置

它不是我新加的一块功能，而是把已有的"**内容价值**"维度从"这条内容对我有没有用"扩展到"这条内容说的对不对"。现在的画像是**横向的**（你看的是什么、和你的目标差多远、有没有变窄），这一步是**纵向的**（单条内容本身站不站得住）。前者的结论永远只对"样本分布"负责，后者必须对"这条内容的具体断言"负责——两者的证据标准和免责口径完全不同，实现时要分开写、分开显示。

它也天然接住了老师建议里的两条：完整推荐一个事件的多方位报道、分析内容的营养价值。区别在于：那时靠人工维护的参考池，这里是靠外部检索自动化——**能力更强，风险也更高**。

### 8.3 它大概怎么跑（叙述，不是实现方案）

1. **门控**：先判断这条内容该不该被核验。娱乐、vlog、纯观点、玩梗类的"对错"没有意义，核验它们只会制造噪音和误报。判断依据可以来自已有的 `topics` 与打标得到的 `content_type`，而不是再引入一个新模型。
2. **抽断言**：从标题、简介、热评里抽出**可被外部核验的具体陈述**（数字、时间、事件、因果、引用），而不是对整条内容给一个笼统的"真/假"。一条视频里可能只有一两句话是可核验的，其余是作者观点——这个区分必须在输出里体现。
3. **求证**：拿这些断言去检索，找**多个独立来源**，看它们是否一致。关键不是"搜到了什么"，而是"**是否互相矛盾**、是否只有单一来源、是否明显偏离常识或官方口径"。
4. **分档输出**：与事实不符 / 部分偏离 / 信息不完整（这个事件还有别的维度没讲）/ **无法判定** / 未发现问题。前两档才主动打扰用户，后两档静默，用户点开才看得到。

### 8.4 必须提前想清楚的边界（不排期，但会影响设计）

- **"搜不到"不等于"错"**。绝大多数真实内容你搜不到反证，这不是错误证据。没有证据时唯一诚实的输出是"无法判定"。
- **观点与事实必须分开**。视频里"我认为 X 会崩"不是可核验断言；"X 在 2024 年涨了 30%"才是。把观点当事实核验，是这个功能最容易出的丑。
- **单一来源不能算"一致"**。两个媒体转同一篇通稿不算两个来源。
- **时效**：去年的数据今年可能已经变了，结论要带时间戳与适用范围。
- **打扰成本不对称**：误报"这条是错的"比漏报一次更伤——用户一旦被冤枉两次，就会关掉弹窗，功能等于废掉。阈值应当明显偏向"不打扰"。
- **和现有免责口径一致**：不能说"这条内容虚假"，只能说"在检索到的来源里存在矛盾/未找到支持"；每条结论必须能点到具体链接。
- **成本与延迟**：每次点击至少一次检索 + 一次判定，比现在的打标贵一个量级。可能需要"只对用户停留超过 N 秒或主动点开核验按钮的内容做"，而不是每条都跑。

### 8.5 与现有代码的衔接点（只点到位置，不展开设计）

- 记录层：`ContentItem` 已有 `topics`、`value_notes`、`facets`，核验结果适合挂在 `value_notes`（扩展）或新开一个平行字段，而不是塞进现有的打标结果里混用。
- 分析层：现有六条规则都是**窗口级统计**，核验是**单条内容级**判断，不要写成第七条 alert——它会污染提醒的语义。
- 交互层：抽屉现在有「结论 / 主题分布 / 建议 / 可以点开看看 / 我的目标」，核验提示适合作为视频页上的**独立浮层**（用户在视频页时才有意义），而不是塞进抽屉。
- AI 出口：新增检索与判定仍然只能走 `ai.js`（外加一个新的"外部检索"工具），保持单一出口与账号级成本可控。

### 8.6 建议先把这三件事定下来再动手

1. 判定结果的档位与文案（尤其"无法判定"这一档要不要给用户看）；
2. 打扰策略（什么情况下主动弹、什么情况下静默）；
3. 检索源范围与来源可信度分级（否则"多来源一致"这句话站不住）。
